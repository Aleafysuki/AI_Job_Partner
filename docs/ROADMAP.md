> v0.3 原有的 `job.input_image`（岗位截图 OCR）**没有**随v0.3 一起完成 ——
> 它在 v0.5 才落地，且实现方式换成了双端统一的本地 tesseract WASM。
> 为避免「版本号解锁了没做的功能」，这一项在 v0.3/v0.4 期间被移到了 `future`，
> v0.5 实现后再挂回`since: 'v0.5'`。这条是本项目最重要的一条版本纪律：
> **版本号只解锁真的做了的**，详见文末「能力落地审计」。
>
> v0.2 的主题由用户在 v0.1 交付后追加，因此原本排在 v0.2 的四项（OCR、最低画像、简历建议、报告导出）
> 顺延到 v0.3，原 v0.3 的四项顺延到 v0.4。这是路线图重排，不是功能削减。
>
> 「面试复盘」同样是用户追加的需求，处理方式与「能力问诊」一致：
> 能力表的 `since` 标 `v0.2`、`docRef` 标「V0.2 追加需求（面试复盘）」，
> **不新开版本槽位** —— 这样既有的「原 v0.2 计划顺延」系列断言全部保持成立。
>
> 这一项不触碰任何铁律：`restrict.full_interview_system`（完整面试系统）说的是
> 「不做端到端面试官系统」，而复盘工具是求职者自己用的，且**刻意不做实时提示**
> —— 面试进行中不产出任何结论。

## v0.2 做成了什么

v0.2 要回答的是 v0.1 暴露出来的三个问题：

> 报告说「RAG 检索增强：缺少证据」，但用户明明做过 —— 他不知道怎么把它变成证据；
> 换一个岗位重新整理简历后，之前积累的证据又得从头再来一遍；
> 知道缺什么之后，没有下一步的具体动作。

| 能力 id | 解决的问题 |
| --- | --- |
| `skill.assess` | 用一组递进问答，把「熟悉 X」问成可判断的掌握程度 |
| `evidence.from_assessment` | 把问诊里说清的具体部分，写成一条证据补进能力库 |
| `library.cross_job` | 换岗位、重新导入简历时按去重键合并，不覆盖已有积累 |
| `training.weak_point` | 按这次匹配里真实没答上的要求出训练题 |
| `training.progress` | 记录作答与自评，训练计划保留在本地 |

### 追加部分解决了什么

用户追加的问题：**面试说完就过去了，事后只剩一个模糊印象** ——
「感觉还行」「有几个问题没答好」，但说不清哪里没答好、岗位到底是不是自己想的那样。

| 能力 id | 解决的问题 |
| --- | --- |
| `interview.record` | 面试过程留存下来；分片落盘，中断不丢已录内容 |
| `interview.record_system_audio` | 线上面试能同时录到面试官那一半对话 |
| `interview.transcribe` | 把录音变成可检索、可分析的文本 |
| `interview.debrief` | 把「机会侧 12 维 + 表现侧 6 维 + 适配度」整理成可复核的报告 |
| `interview.debrief_export` | 离线 HTML，断网可开 |

三条设计边界（不是「暂时没做」，是**刻意不做**）：

1. **不做实时提示。** 面试进行中不产出任何结论 —— 这个工具用在面试之后，不用在面试当中。
2. **录制的默认行为是静默**：不弹 toast、不弹窗、不弹系统通知、不改窗口标题、窗口隐藏到托盘。
   面试时屏幕上多出来的任何东西都可能被对方看到，而这件事跟复盘本身毫无关系。
3. **不预测面试结果**，也不评价面试官。

### 这一版最重要的一条规则

**问诊补充的证据强度封顶为「中」。**

理由：证据强度衡量的是「这条经历能不能被外部核对」，而问诊是自述，没有外部载体。
如果允许问诊产出「强」证据，产品就等于自己废掉了 v0.1 立下的判断标准。
想升级到「强」只有一条路：补上链接、数字、时间这类可核对的东西 —— 补完系统会自动重算。

规则实现在 `domain/evidence.ts` 的 `MAX_STRENGTH_BY_ORIGIN` 与 `capStrengthByOrigin()`，
并在 `finalizeProfile()` 里同样生效（否则每次归一化都会把封顶悄悄绕过去）。这一条有专门的单测。

### 另外两条防止「自欺」的规则

1. **单次问诊给不出「可讲清取舍」**（`expert`）。那需要多场景使用，不可能从一次问答里得到；
   除非能力库里已经有该技能的项目 / 工作 / 开源类证据。
2. **用户说「没做过」时，场景词不能把等级抬上去**。
   问诊里有一个独立的 `denial` 信号，一旦命中，等级最高只能到「了解概念」。

这一批修的不是新功能，是**一个假闭环**：用户填了问诊、练了训练，但两者都不进能力库，
于是匹配结论永远不变，而界面上却写着「练完去重跑匹配」。用户照做发现什么都没变，
观感就变成「我填的东西不算数，要我重填」。任务书见 `docs/TASK-v06-evidence-loop.md`。

| `assess.ai_summary_review` | AI 把口述回答整理成档案条目，**每条必须带用户原话出处**，对不上就丢弃并明说 |

## 怎么用这套东西

### 假设现在要做 v0.3

1. 打开 `packages/core/src/version.ts`；
2. 把 `CURRENT_RELEASE` 从 `'v0.2'` 改成 `'v0.3'`；
3. 完成 —— `job.input_image` 等四项的 `isEnabled()` 立刻返回 `true`，界面上对应的 Coming Soon 卡片自动消失。

### 假设产品方向调整，决定要做一个爬虫

1. 在能力表里找到 `restrict.job_crawler`；
2. 把 `since: 'future'` 改成 `since: 'v0.5'`；
3. 把 `CURRENT_RELEASE` 提升到那个版本；
4. 此时 `isEnabled('restrict.job_crawler')` 返回 `true`，才可以开始写实现。

在 `since` 没改之前，任何试图绕过能力开关直接实现该功能的代码都属于违反项目约束。

### 假设要临时验证某个高版本行为（不写盘）

```ts
import { setReleaseOverride } from '@aijob/core';
setReleaseOverride('v0.4');   // 仅在当前运行时生效，不会持久化
```

## 尚未处理的已知问题

| 问题 | 影响 | 计划 |
| --- | --- | --- |
| PDF 扫描件没有文字层时无法解析 | 需要用户手动粘贴 | v0.3 接 OCR |
| 技能词典覆盖不到长尾能力名 | 这类要求会落到「无法判断」；训练题退回通用要点 | 持续补词典；问诊可手动输入技能名 |
| 本地规则引擎对段落格式依赖较强 | 排版奇特的简历可能切分不准 | 建议配一个模型，或改用手动输入经历 |
| 匹配只做单岗位 | 无法同时比较多个岗位的优先级 | 后续版本（文档 21 节） |
| 训练题不判断回答对错 | 自评是主观的，系统不假装能替用户打分 | 真实面试反馈已由「面试复盘」补齐（v0.2 追加） |
| 面试转写的说话人靠语用特征推断 | 单声道录音分不清谁在说话；标错会污染表现侧评分 | 界面明确标注「可人工核对」；双声道采集是后续可做的事 |
| macOS / Linux 的系统内录需要虚拟音频设备 | 这两个平台上内录可能拿不到声音 | 会自动降级为「只录麦克风」并如实告知；不做自动装驱动 |
| 复盘只做单场面试 | 无法横向比较多次面试的表现变化 | 后续版本（把多次报告放在一起看） |
| 合并按「类型 + 标题 + 内容前缀」去重 | 同一件事用两种写法写会被当成两条证据 | 目前靠人工合并；后续可加语义去重 |
| **Android 端不做系统内录** | 线上面试录不到面试官那一半对话，表现侧部分维度只能标「无法判断」 | 平台边界（`AudioPlaybackCapture` 需要被录方同意，会议类 App 普遍关闭），不做；见 `docs/ANDROID.md` |
| **Android 端静默模式必有常驻通知** | 与产品「面试期间不弹系统通知」的边界相悖 | Android 强制要求前台服务显示通知，无法绕过；已压到最低可见度，并让该通知承担「结束录制」的安全出口 |
| **Android 端无全局快捷键** | 桌面端的两条安全出口在移动端只能保留一条 | Android 没有全局快捷键概念；由常驻通知替代 |

| 手机不适合长时间面试录制 | 需屏幕常亮、耗电、易误触 | 产品上建议面试复盘优先用桌面端，移动端适合会后补录与查看 |
| Android 8 以下设备被排除 | `minSdk = 26` | 为自适应图标与 `java.nio.file` 让路；26 已覆盖几乎所有在用设备 |

## 决策记录：`restrict.mobile_client` 为什么没有解锁

**日期**：2026-09-29
**决策人**：用户（项目所有者）
**结论**：**不动能力表，`restrict.mobile_client` 保持 `since: 'future'`。**

### 背景

产品需求是「把这个项目做成 Android 平台的 APP，设计语言参考 Metro」。
而能力表里有一条：

```ts
{ id: 'restrict.mobile_client', label: '移动端独立客户端',
  description: 'Android / iOS 独立客户端', since: 'future', docRef: '25', restriction: true }
```

它来自文档第 25 节的「暂时不做」，按规则不会随版本号自动解锁；
本文件开头也写着「在 `since` 没改之前，任何试图绕过能力开关直接实现该功能的代码，
都属于违反项目约束」。所以这件事必须显式决策，不能悄悄做。

### 判断依据

第 25 节那批条目的共同特征是「另起一条产品线或服务体系」：
招聘网站爬虫、职位数据库、自动投递、用户注册、在线支付、社区、企业招聘后台……
`mobile_client` 排在其中，指的是**另做一个移动端产品**
（独立的功能集合、独立的数据、可能还要配套账号体系与云同步）。

而本次交付的是**同一个客户端换一个宿主**，四条都不成立：

1. 数据仍是本机单份，不建账号、不上云
   （为此还把 `allowBackup` 从模板默认的 `true` 改成了 `false`）；
2. 功能集合与桌面端逐个对齐，没有多一项也没有少一项；
3. 判断逻辑仍全部在 `packages/core`（`tsconfig` 的 `lib` 只有 `ES2023`，
   越界即 typecheck 失败 —— 这是「逻辑没被分叉」的机械证明）；
4. 界面是**同一份代码**，只是按宿主换外壳（`desktop` / `android` 两个 Shell）。

所以这次不是「第二个客户端」，而是「同一份东西的第二个壳」，
与第 25 节要防的事不是一回事 —— 能力表不需要改。

### 复现条件（重要）

这个结论**只在上面四条都成立时有效**。如果以后要做的是：

- 移动端专属功能（桌面端没有的）；
- 移动端账号、云同步、多设备；
- 或者移动端独立的数据模型；

那就变成了第 25 节说的「独立客户端」，**必须先按正常流程把
`restrict.mobile_client` 的 `since` 显式改成目标版本，再动代码。**

### 顺带说明：为什么没有新开版本槽位

另一条备选方案是新增 `v0.2-mobile` 槽位并解锁该能力。
没有采用，是因为这个方案会引入一个副作用：`CURRENT_RELEASE` 一旦抬高，
`releaseReached()` 会连带解锁 v0.3 / v0.4 的四项尚未实现的能力，
而 `tests/core-pipeline.test.ts` 里「原 v0.2 计划顺延」那组断言会全部失效。
既然本次不触碰能力开关，就没有必要为了记一件事去改版本号。

详细实现与平台差异见 `docs/ANDROID.md`。

3. **匹配结论与能力层级只能标「大致对应」，不能标「精确」** ——

### v0.4：模拟面试（`domain/mock-interview.ts` + `engines/mock-interview.ts` + `pages/Mock.tsx`）

四个能力串成一条链：出题 → 逐轮追问 → 五维分析 → 薄弱点回流。

**最关键的产品立场：不生成任何「你可以这样回答」的内容。**
这与 `training.reference_answer`（训练题给参考答案）是**刻意不同的**：
训练题有客观对错，参考答案帮用户确认「我懂了」；模拟面试是开放表达，
给出参考话术会诱导背诵，而背下来的表达在第三轮追问下必然崩。

三条实装中被测试逼出来的判断：

1. **期望点的「有没有答到」判定只能用 `includes`**，不能叠 `textMentionsSkill` ——
   后者只认技能词典内的词，而期望点可能是「缓存淘汰策略」这类自定义短语，
   叠上它会把整份期望点都判成缺失。
2. **表达类维度（结构 / 篇幅）不进能力库**。那是练几次就能改的，
   写进跨岗位保留的技能等级里，对任何岗位的判断都没有贡献。
3. **压力题必须排在最后**。一上来就问「你错了怎么办」，大多数人会当场乱掉，
   后面的正常问题也答不好。

### v0.3：三项（`match-report-render.ts` + `resume-advice.ts` + `minimum-candidate.ts` 重写）

- **报告导出**：自包含离线 HTML（内联 CSS、不依赖 CDN、窄屏下表格转键值对）。
  **不提供 0–100 匹配分** —— 导出件最容易被简化成「他匹配度 78%」，
  而这个数字在原产品里就被明确否决过。
- **简历建议**：只针对具体岗位，不给通用模板。
  **绝不为「你补一个 Redis 项目」这种建议** —— 那是替用户编造，
  编出来的东西在面试第二个问题就会崩。所以建议只能指向用户已写过的内容，
  并同时展示「你原来写的」与「建议改成」。
- **最低画像**：只列硬性缺口，不列优化项；每一项都带来源要求 id；
  不给「够不够」的二元结论。

## 一、OCR：为什么必须本地推理

候选方案四个，逐一说明取舍：

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 云端 OCR API（百度/腾讯/Google） | **排除** | 截图里往往含公司名、薪资、地址、HR 私聊内容，上传即泄露。而「数据只在本机」是这个产品的第一承诺，一次违约就再也回不去了。 |
| 打包 PP-OCR ONNX + onnxruntime | 未采用 | 中文检测+识别+方向分类三个模型合计 10MB+，且要为 WebView 与原生两套运行时各准备一份，还要自己写预处理。 |
| ML Kit on-device（Android） | **采用（手机端）** | 模型由 Google 以 AAR 打包进 APK（约 2MB），推理完全在设备上，零网络请求。 |
| tesseract.js WASM（桌面端） | **采用（桌面端）** | ML Kit 是 Android 专有的。WASM 方案让桌面端也能离线跑，核心 4MB + 中文数据 2MB 全部随 npm 包分发。 |

**两个宿主同一份契约、不同引擎**，不是偷懒：
统一到 WASM 会让手机（主战场）识别率掉一截；
统一到 ML Kit 则桌面端根本没这个能力。

实测差异：桌面 WASM 约 0.7 秒识别一张 JD 截图（7 行全对），
Android 原生预期 2–4 秒。桌面端中文小字识别率明显弱于 ML Kit，
所以界面上要如实告知用户「现在是哪个引擎在跑」，而不是掩盖差异。

## 二、三条不能省的 OCR 约束

1. **识别结果必须经用户核对才进解析链路。**
   识别不准比识别不了更危险 —— 用户会把「没认全」当成「JD 就这么多」。
   界面上展示置信度，低置信度的块单独列出来。

2. **置信度判定不能只看均值。**
   一张「平均 0.85 但有三行是 0.3」的截图，对用户来说与「每行都 0.85」完全不同。
   实现在 `summarizeConfidence`。

3. **不静默截断超大图片。**
   超限时明确报错并建议裁剪 —— 截断出来的文本一定残缺，而用户不会知道。

## 三、问答交互化：问题从上一个回答里长出来

新增 `engines/interactive-followup.ts`，核心是 `extractFollowUpHooks`：
从用户回答里抽「可追问的点」，下一轮问题**从这些点里长出来**，而不是按题单顺序取。

抽哪几类点（按优先级）：

| 类型 | 触发信号 | 为什么追这个 |
| --- | --- | --- |
| 模糊量词 | 「大概」「应该」「记不清」 | 它同时说明两件事：没把握、手上没有可核对的东西 |
| 自我怀疑 | 「不太会」「没搞懂」 | 问「你会怎么从零弄明白」而不是「你打算怎么学」—— 前者是行动，后者是态度 |
| 没有机制 | 有长度但无「因为/原理/机制」 | 「做过」和「知道为什么这样做」在面试里是两个价位 |
| 技能无证据 | 提到某技术但无场景 | 「用过 X」而没场景是简历上最常见的空话 |
| 没讲完 | 结尾是「就是」「然后」 | 让他说完，比追问有效 |

**三条硬约束**（都有断言钉住）：

1. **每个追问点必须带 `anchor`（用户原话）**。
   没有原文就追问等于凭空编，用户会困惑「我哪句没说清」—— 那比不追问更糟。
2. **必须能终止**：最多追 2 下、每题最多 3 轮、回答短于 40 字不追。
   每次都追的话 5 题会变 20 题，用户会放弃。
3. **反馈只说缺什么，不给该怎么说** —— 与 Prep、模拟面试同源。
   反馈判据只用可核对信号（长度、有无因果、有无数字、有无场景），不评价文风。

## 四、顺带修掉的一个真 bug：`check-native.mjs` 自己出错

新加的两个 Java 文件被误报「括号不配对」，但它们的括号是对的。

根因：脚本的剥离顺序是「先注释、后字符串」。
`"content://"` 里的 `//` 被当成行注释，于是**整行剩下的代码被删掉**，
花括号随即不配对。

修法是改成「先字符串、后注释」。

**教训**：静态检查器自己出错比它漏报更麻烦 —— 它会把正确的代码判成错的，
本轮就差点让人去改本来正确的 Java。
