> 来源与状态：本目录留档的是 `multi-dimension-fit-report` 这个 Skill 的原始参考文件，
> 本项目的实现以它们为蓝本。**运行时不读取这里的文件** —— 机器可读的维度定义在
> `packages/core/src/debrief/dimensions.ts`，提示词在 `packages/core/src/ai/prompts.ts`，

> 修改维度时必须同步三处：`debrief/dimensions.ts`、本目录的 `framework.md`、`docs/DATA_MODEL.md` 的维度表。

# 12 维度完整规范

本文件是分析阶段的权威依据。机器可读版本见 `dimensions.json`，两者必须保持一致。

每个维度统一包含：**目标 → 分析步骤 → 表样 / 清单 → 禁忌**。产出的 JSON 结构见 `SKILL.md` Stage 2。

写作通则：

- 每条 finding 必须挂 `evidence_ids`，且 `basis` 只能取 `stated` 或 `inferred`，不在同一句里混用。
- 维度内证据不足以支撑结论时，`status = insufficient_info`，把缺口写进 `unknowns`，**不要拿行业惯例填空**。
- 所有维度的表述要能被外行读懂。行业专有名词要么加一句解释，要么换成通用描述。
- 跨行业泛化：讨论"这份工作"时，永远用"该角色 / 该岗位 / 该机会"的中性表述，不要假设行业。

## D1 · 实态还原：这个角色到底在干什么

**目标**：用普通人的语言还原真实工作流程，而不是复述岗位描述。区分"对方说的"和"实际会发生的"。

**步骤**

1. 逐条列出对方描述的工作内容（保留原话要点）。
2. 还原一个普通员工一天可能经历的流程，用箭头串起来。示例形态：
   - 沟通前置型：上班 → 查看任务列表 → 发起接触 → 对方回应（配合 / 拒绝 / 质疑）→ 说明来意 → 记录结果 → 处理后续 → 下一轮 → 下班
   - 交付型：上班 → 查看待办 → 阅读需求 → 执行与自测 → 提交 → 评审反馈 → 修改 → 同步进展 → 下班
   - 创意型：上班 → 接收需求 → 研究参考 → 构思 → 出稿 → 内部评审 → 修改迭代 → 交付 → 归档 → 下班
   - 分析型：上班 → 确认需求 → 取数与清洗 → 分析建模 → 出图与结论 → 汇报 → 反馈修改 → 归档 → 下班
   - 运营型：上班 → 查看计划 → 内容策划与产出 → 发布 → 数据监控 → 用户互动 → 复盘 → 调整策略 → 下班
   - 事务型：上班 → 查看当日事务 → 处理邮件与公文 → 协调资源 → 会议组织与记录 → 归档 → 处理临时事务 → 下班
   - 执行型：上班 → 岗前准备 → 领取任务或物料 → 执行 → 质量检查 → 记录产出 → 交接 → 下班
   
   以上只是形态参考，**必须按文本实际内容重组，不能直接套用**。
3. 信息足够时为每个环节估一个耗时区间。
4. 标注哪些来自原文、哪些是推断。

**禁忌**：复述招聘话术；把对方说的当成既成事实；用行业惯例补齐缺失环节。

## D2 · 要求拆解：硬性要求与隐性要求

**目标**：拆成两部分——可量化或明确规定的**硬性条件**，以及实际存在但没写出来的**软性代价**。

**步骤**

1. 对照 `hard_requirements` 清单（14 项）逐项填「满足 / 不满足 / 未知」。
2. 对照 `implicit_requirements` 清单（10 项）逐项评要求强度 1–5，并写出判断依据。
3. 把"对方明说的门槛"和"实际会筛人但没说出口的门槛"分开列。
4. 汇总为「要求综合评估」雷达图数据。

**硬性要求检查清单（14 项）**

| 检查项 | 分析要点 | 适用范围 |
|---|---|---|
| 每天工作多少小时 | 声称时长 vs 排班安排 | 全行业通用 |
| 每月休息多少天 | 不同发言人说法是否一致 | 全行业通用 |
| 是否固定排班 | 班次类型、轮换频率 | 制造业/医疗/零售/客服等 |
| 是否需要节假日工作 | 节假日安排与补偿 | 服务业/互联网等 |
| 每日任务或指标数量 | 联系数、工单数、产出件数 | 视岗位而定 |
| 是否有业绩或创收指标 | 回款 / 销售额要求 | 销售/商务/项目管理/运营等 |
| 是否有单次处理时长要求 | 通话最低时长、响应时限 | 客服/技术支持/开发等 |
| 是否有成功率或完成率要求 | 接通率、转化率、通过率 | 销售/客服/审核/开发等 |
| 是否有质量审核或抽检 | 质检形式、标准、是否影响收入 | 全行业通用 |
| 是否有 KPI | 所有量化考核汇总 | 全行业通用 |
| 是否有迟到或未完成任务的处罚 | 扣钱 / 警告 / 淘汰 | 全行业通用 |
| 是否需要加班 | 要求与补偿方式 | 全行业通用 |
| 是否需要培训 | 时长、是否带薪、有无绑定条件 | 全行业通用 |
| 是否需要使用特定系统或工具 | 系统名称与操作复杂度 | 技术/运营/财务/设计等 |

**隐性要求检查清单（10 项）**

| 检查项 | 分析要点 | 适用范围 |
|---|---|---|
| 是否需要持续主动输出 | 是否要求不停沟通或产出 | 视岗位而定 |
| 是否经常面对否定或驳回 | 方案被拒、代码被打回、客户拒绝 | 设计/开发/销售/客服等 |
| 是否需要处理负面情绪 | 是否经常面对愤怒、质疑、投诉 | 客服/销售/行政/HR/社工等 |
| 是否需要说服或影响他人 | 工作成效是否依赖改变对方意愿 | 销售/商务/项目管理/市场等 |
| 是否需要快速反应 | 临场应变、即时作答 | 客服/运营/急诊/交易等 |
| 是否需要长期保持注意力 | 长时间连续专注 | 技术/分析/审核/驾驶等 |
| 是否需要记忆复杂流程 | 流程、规范、话术的记忆量 | 金融/法律/医疗/客服等 |
| 是否需要多任务或多工具切换 | 并行系统、并行事项 | 运营/行政/项目管理/交易等 |
| 是否需要承受过程监控 | 实时查看进度、录音质检 | 全行业通用 |
| 是否存在数量与质量双重考核 | 既要求快又要求好 | 全行业通用 |

**禁忌**：把清单里出现的关键工具名、规范编号、专业概念解读成"可以学"；把"不限经验/不限学历"当成低门槛。

## D3 · 工作量测算

**目标**：把关键数量指标换算成时间，判断在正常工作日内是否物理可行。

**步骤**

1. 提取所有关于工作量的描述。不同发言人说法不同的一并列出。
2. 区分关键概念：名义口径（做了多少下）与有效口径（达成多少结果）。
3. 按不同单位耗时做多档情景模拟。
4. 计算纯处理时间与剩余时间，给出可行性判断。
5. 补上常被忽略的时间成本：查看任务详情、系统切换、等待响应、处理突发问题、情绪恢复、填写记录。

**时间测算表（按每日 8 小时连续处理）**

| 平均每项处理时长 | 纯处理时间 | 剩余时间 | 可行性判断 |
|---|---|---|---|
| 30 秒 | 约 85 分钟 | 约 365 分钟 | 轻松完成 |
| 1 分钟 | 约 170 分钟 | 约 280 分钟 | 可以完成 |
| 2 分钟 | 约 340 分钟 | 约 110 分钟 | 紧张但可行 |
| 3 分钟 | 约 510 分钟 | 超出工作日 | 不可能完成 |

表按 170 个 / 日标定；每日指标换成其他数量时按同比例缩放，并在 `computation.inputs` 中写明缩放依据。

**补充考虑**：额外时间成本；对方关于工作时长说法的可信度；是否存在"基础数量 + 其他 KPI"的多重考核。

**禁忌**：直接把数量当成累或简单；忽略记录、切换、等待、情绪恢复；用单一档位代替多档情景。

## D4 · 压力画像

**目标**：把"压力大"拆成可分别定级的类型，每类独立给等级与依据。

**步骤**：对 9 类压力逐项定级「低 / 中 / 高 / 信息不足」，每类写出对应证据编号，汇入压力雷达。

| 类型 | 判断等级 | 分析依据（示例问题） |
|---|---|---|
| A. 数量压力 | 低/中/高/信息不足 | 每天必须完成多少任务 |
| B. 时间压力 | 低/中/高/信息不足 | 是否存在单位时间内必须完成的要求 |
| C. 业绩压力 | 低/中/高/信息不足 | 是否必须完成一定金额或转化结果 |
| D. 情绪压力 | 低/中/高/信息不足 | 是否经常面对否定、拒绝、投诉 |
| E. 监控压力 | 低/中/高/信息不足 | 是否被实时查看进度或录音质检 |
| F. 注意力压力 | 低/中/高/信息不足 | 是否需要长时间连续重复专注 |
| G. 沟通压力 | 低/中/高/信息不足 | 是否需要临场解释、争辩、说服 |
| H. 排班压力 | 低/中/高/信息不足 | 是否存在长期早晚班、轮班、节假日 |
| I. 身体压力 | 低/中/高/信息不足 | 是否需要久坐、久站、重体力或高频移动 |

**禁忌**：只给一个笼统的"压力大"；等级留空（信息不足必须显式写 `unknown`）。

## D5 · 名义口径 vs 实际口径

**目标**：指出同一指标在两种口径下的强度差异。这是最容易被话术掩盖的位置。

**步骤**

1. 列出所有"N 个 / N 单 / N 稿 / N 个功能"类指标。
2. 为每个指标写出名义口径与实际口径各自含义。
3. 判断考核的是哪一个口径；没说明的标未知，并落到问题清单。

**常见对照**

| 名义口径 | 实际口径 | 被掩盖的成本 |
|---|---|---|
| 拨打 N 个电话 | 有效沟通 N 个电话 | 大量未接通、关机、拒接 |
| 提交 N 个方案稿 | 通过评审的 N 个方案稿 | 需要大幅修改重做 |
| 开发 N 个功能 | 上线稳定的 N 个功能 | 联调与 debug 修复 |
| 联系 N 个客户 | 成功签约 N 个客户 | 大量拒绝与无效沟通 |

**禁忌**：只列数字不区分口径。

| 工作类型 | 典型特征 |

| 客户服务类 | 以接听或回复客户咨询为主 |
| 售后/运维类 | 处理售后问题、维护客户或系统稳定 |
| 销售/商务类 | 以促成交易、签单、拓展客户为主 |
| 追款/风控类 | 以追回欠款、降低坏账风险为主 |
| 客诉/公关类 | 处理投诉与危机沟通 |
| 商务沟通类 | 以谈判、合作洽谈、对外联络为主 |
| 运营类 | 以内容、用户、活动运营为主 |
| 数据/分析类 | 以数据处理、分析、报表为主 |
| 审核/质检类 | 以内容审核、质量检查为主 |

## D7 · 个体适配

**目标**：基于当事人条件逐项分析适配度。**不给单一总分**，每项独立分析，有依据有出处。区分"理论上能做"与"能长期做"。

**步骤**

1. 对照 10 个适配维度逐项给 1–5 分或 `null`。
2. 每项写明与当事人哪句描述相关。
3. 明确标出当事人心理边界被触碰的维度。

| 适配维度 | 分析要点 | 泛化说明 |
|---|---|---|
| ① 技能适配度 | 现有技能与要求的重合度 | 含硬技能与工具熟练度 |
| ② 沟通适配度 | 所需沟通量与强度 | 含电话、书面、面谈、演示 |
| ③ 重复劳动适配度 | 重复性与个人耐受度 | 含重复沟通、重复操作、重复审核 |
| ④ 注意力适配度 | 注意力要求与个人习惯 | 含长时间盯屏、持续专注、频繁切换 |
| ⑤ 情绪压力适配度 | 情绪消耗与承受力 | 含面对负面情绪、被拒绝、被质疑 |
| ⑥ KPI 适配度 | 量化考核压力与工作风格 | 含数量指标、质量指标、双重考核 |
| ⑦ 排班适配度 | 排班方式与生活安排 | 含早晚班、大小周、倒班、节假日 |
| ⑧ 身体劳动适配度 | 身体要求与个人体能 | 含久坐、久站、重体力、通勤强度 |
| ⑨ 短期过渡适配度 | 作为过渡工作的整体适配 | 综合前八项，结合时间预期 |
| ⑩ 长期发展价值 | 技能积累与可迁移性 | 客观描述能积累什么，不夸大 |

**禁忌**：用总分代替逐项分析；把当事人说"可以试试"解读成"能长期承受"；越过当事人边界替他做取舍。

## D8 · 持续性推演：能不能撑住

**目标**：分三个时间尺度分析，区分"理论上能完成"与"可以连续完成而不崩溃"。

**步骤**

- **第一天**：可能遇到什么情况（第一印象、上手流程、第一个任务）；心理感受预测；当天任务能否完成。
- **第一周**：最可能出现什么问题（工作量超预期、协作摩擦、技能不足）；新鲜感消退后的现实冲击；需要警惕的早期信号。
- **第一个月**：真正决定能否留下的因素；"理论上能完成"与"连续一个月不崩溃"的差距在哪里。

**关键区分维度**

| 维度 | 理论上能完成 | 可以连续完成不崩溃 |
|---|---|---|
| 体力/精力 | 某一天咬牙能撑住 | 连续 22 天都能保持基本状态 |
| 情绪 | 偶尔面对负面情绪能处理 | 每天面对负面情绪不会持续积压 |
| 心理压力 | 知道目标后觉得应该能完成 | 不需要每天靠意志力硬扛 |
| 身体反应 | 没有明显身体不适 | 不会出现失眠、头痛、持续性疲劳 |
| 工作满意度 | 不讨厌这份工作 | 对工作内容不产生强烈抵触 |

**禁忌**：只判断单日可行性；用"坚持一下就好"替代机制分析。

## D9 · 话术风险扫描

**目标**：识别文本中的风险信号。**不武断判定为说谎**，而是分析每句话可能意味着什么、以及如何验证。详细信号库与逐句模板见 `risk-signals.md`。

**步骤**

1. 按信号库扫描，命中即收录。
2. 每条给：正面理解 / 反面理解 / 其他可能。
3. 写清如何验证：要问什么、要观察什么。
4. 不同发言人说法不一致处单独列出。

**禁忌**：把单条话术直接定性为欺骗；只标风险不给验证路径。

---

## D10 · 实际回报测算

**目标**：按可确定的信息计算单位时间回报，而不是只看名义收入。

**步骤**

1. 提取 7 项输入：月薪构成、工作天数、每日工作时长、休息是否计入、加班、节假日补贴、社保扣除。
2. 分情景 A（理想）/ B（正常）/ C（最差）给出单位时间回报区间，并写明每个情景的假设。
3. 分析薪酬区间对应何种劳动投入。

| 项目 | 需要从文本中提取 |
|---|---|
| 月薪 | 底薪、绩效范围、综合到手 |
| 工作天数 | 月休天数 |
| 每天工作时长 | 班次时长、是否含午休 |
| 是否包含休息时间 | 午休时长、自由支配时间 |
| 加班 | 是否需要、加班费计算方式 |
| 节假日补贴 | 节假日工资计算方式 |
| 社保扣除 | 个人承担部分 |

公式：`单位时间回报 = 实发月收入 ÷ (月工作天数 × 每日净工作时长)`

**禁忌**：用名义月薪直接下结论；忽略午休是否计入、加班是否另计。

## D11 · 入职前必须问清的问题

**目标**：产出 10–15 个具体到可以直接复制发送的问题。

**步骤**：按五类分组，优先覆盖信息不一致处与影响收入的因素，每条标优先级并写明要验证哪个维度。

| 分类 | 数量 |
|---|---|
| 关于工作量和 KPI | 3–4 |
| 关于薪酬和福利 | 3–4 |
| 关于工作时间和排班 | 2–3 |
| 关于工作环境和内容 | 2–3 |
| 关于组织和岗位 | 2–3 |

**问题设计原则**：非常具体，避免开放式；可直接复制发送；优先问信息不一致处；优先问影响收入的因素；包含验证前面分析疑点的问题。

**可复用示例（按实际岗位改写）**

- 每日 X 个任务是"名义上联系 X 个"还是"有效完成 X 个"？两者区别是什么？
- 平均每项任务处理时长是多少？
- 每日任务量是硬性 KPI 还是参考数量？
- 完不成任务指标会有什么后果？
- 是否有业绩或创收指标？具体数值是多少？
- 薪资区间的构成是什么？基本工资多少、绩效占多少？
- 有没有全勤奖、罚款、扣绩效？
- 是否需要加班？加班费怎么算？
- 法定节假日怎么计算工资？
- 是否有质量审核或抽检？标准是什么？
- 是否会被实时查看工作进度？
- 工作过程中是否会遭遇大量拒绝、投诉或冲突？
- 培训期是否带薪？培训多久？
- 试用期工资多少？社保什么时候缴？
- 离职需要提前多久？是否存在其他隐性考核？

**禁忌**：开放式提问；少于 10 条或多于 15 条；问题无法直接复制发送。

## D12 · 情景推演与决策表

**目标**：不给"去 / 不去"的简单结论，而是给出三种情景推演与三档条件决策表。

**三种情景**

- **情景 A · 对方描述基本可信**：假设哪些条件成立 → 这份工作实际可能是什么样 → 适合什么样的人。
- **情景 B · 描述存在明显水分**：假设哪些情况出现 → 会变成什么样 → 最坏情况下的应对。
- **情景 C · 当事人有特定优先需求**：最应该重点观察哪些指标 → 如何判断是否应该止损。

**决策表**

| 分类 | 条件 |
|---|---|
| 可以考虑 | 哪些条件满足时，可以进入下一步 |
| 需要谨慎 | 哪些条件出现时，需要先验证再决定 |
| 明显不匹配 | 哪些条件出现时，说明这条路不值得投入 |

决策表的条件只能来自 D1–D10 的结论，**不得新造条件**。

**收尾**：写一句边界声明——不替当事人做决定，只把做决定所需的信息整理清楚。最后只给**一个**下一步动作。
